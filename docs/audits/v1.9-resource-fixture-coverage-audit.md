# Arcane Incantations v1.9 — fixture-to-implementation coverage audit

**Status:** Engineering audit; not canonical specification.  
**Audited source:** `docs/canon/arcane-incantations-v1.9-resource-accounting-and-conservation-contracts.md`  
**Source fixtures:** 60 normative expected outcomes.  
**Implementation branch baseline:** `bbcced72fab93ce86905a96a3b80b1c96abad5ce` (v1.9 development branch).

## Purpose and interpretation

This audit connects each of the 60 canonical v1.9 design fixtures to the current resource preflight, ledger projection, conservation evaluator, account reconciler and separate gate tests.

It does **not** execute the 60 specification fixtures. It does not change their expected outcomes, promote implementation behaviour to canon, or claim that a bounded evaluator implements the entire normative contract.

- **BOUNDED:** the linked tests cover the stated bounded behaviour under the implementation's explicit assumptions. This is not a claim that every part of the normative case is complete.
- **PARTIAL:** some relevant behaviour is enforced, but one or more important parts of the fixture remain unimplemented or caller-supplied.
- **SEPARATE-GATE:** the fixture concerns an independent authority/policy gate; it is intentionally not decided by resource accounting.
- **SPECIFICATION-ONLY:** no executable implementation is claimed for the fixture.

A linked test ID identifies implementation regression evidence in the workbench registry. It is not a proof of external evidence authenticity, physical validity or execution.

The automated audit test also verifies that every distinct linked ID resolves to exactly one registry entry, its declared source path remains inside the repository, and its marker appears exactly once in that source test file. This protects traceability metadata; it does not prove that a test has run. Execution evidence still comes from the exact-commit CI workflow.

## Current implementation modules

- `resourcePreflight.ts`: bounded scalar availability; caller-supplied source availability windows and provenance references are checked against an explicit evaluation time, with stale values rejected and ambiguous endpoints left unresolved; source/budget evidence states, held-reservation arithmetic, conservative budget upper bounds and an opaque contract-version reference returned for downstream reconciliation.
- `resourceLedger.ts`: deterministic integer-tick projection for supported source-entry, transfer, reservation, consumption, measured-return and loss events; non-array collections, non-object entries and invalid typed fields produce structured malformed diagnostics rather than uncaught exceptions; idempotency fingerprints retain any supplied contract-version identity; generic transformations, corrections, external exchanges and reconciliation events are not applied.
- `reservationExpiry.ts`: pure temporal assessment using explicit Unix-millisecond timestamps; it requires caller-supplied observed-expiry or contractual-guarantee evidence after the expiry time, leaves the exact boundary unresolved, and never mutates ledger availability.
- `resourceConservation.ts`: one-resource, one-unit-contract scalar-additive balance evaluation, single-account gross-balance comparison and an account-set wrapper that requires one observation per account while reusing the same exact event batch; reconciliation requires exact caller-supplied preflight/report contract-version identity and leaves mismatches unresolved; it does not evaluate a cross-account invariant.
- `resourceReconciliationStage.ts`: pure composition of passing preflight, explicit attempt/report evidence, exact version and observation-time scope, scalar conservation evaluation and account-set gross-balance reconciliation; returns RESOURCE-RECONCILED only for this bounded scope, preserves evidenced mismatches and leaves incomplete evidence unknown.
- `resourceAccountingAudit.ts`: presence-only assessment of the 14 top-level v1.9 invocation-audit sections; preserves a reported outcome verbatim and explicitly does not validate semantic completeness.
- `resourceConservationPreview.ts`: synthetic, deterministic Playground samples only.
- `authorityDecision` and `policyProfileComposition` modules: separate gate concerns; their results are not resource evidence or execution.

## Explicit gaps retained

The current implementation does not supply dimension-vector conservation, source-contract authentication, probabilistic uncertainty models, expiry-driven ledger state transitions or release-policy integration, reservation identity/state resolution, authenticated expiry evidence, concurrent/distributed reservation guarantees, availability-window endpoint policy, valid transformation contracts, complete boundary discovery, independently verified event-batch completeness, executor transaction semantics, partial execution, interruption/recovery, compensation, refund semantics, distributed-ledger consistency, cross-version compatibility/migration, general whole-resource reconciliation beyond the bounded scalar/account-set coordinator, semantic audit-record construction and content validation or target postcondition verification.

No generic mana-to-energy conversion, unit conversion, resource equivalence, new tolerance, physical law or spoken form is introduced by this audit.

## Next step

The bounded scalar/account-set stage composition is now implemented without changing the locked v1.9 source or its 60 normative fixture outcomes. Further expansion must wait for explicit domain contracts and negative fixtures: in particular, RES19-22 needs a defined transformation/conversion contract, RES19-28 needs an evidence-backed boundary-completeness model, and the uncertainty and execution-lifecycle gaps remain unresolved. ### 2026-11-14 — v1.9 audit structure and outcome separation

Added a presence-only assessor for the 14 top-level sections named by the v1.9 §8 RESOURCE-ACCOUNTING-RECORD tuple. It reports absent or undefined sections without filling them. Explicit null and empty values count as represented fields only; they do not prove that their contents or evidence are complete.

The assessor copies a caller-reported resource outcome verbatim, including `RESOURCE-OUTCOME-UNKNOWN` or a failure label, and marks outcome interpretation as NOT-ASSESSED. The read-only Playground sample demonstrates all 14 sections represented as unknown placeholders while conservation and account reconciliation remain unresolved.

RES19-59 is now PARTIAL, not BOUNDED: top-level structure presence is tested, but section content, contract-version validity, evidence authenticity, audit semantics and overall outcome remain unverified. The 60 canonical fixture rows and expected results are unchanged. This work does not construct a trusted audit record, alter a ledger, establish conservation, or claim execution.


### 2026-11-18 — bounded v1.9 account-set transfer reconciliation

Added a pure account-set reconciliation wrapper around the existing single-account reconciler. It requires a non-empty, duplicate-free account set, exact resource/unit-contract agreement, and exactly one measured observation for every account. Each account is compared against the same supplied event batch and retains its own reconciled, discrepancy, unresolved or invalid result. The batch outcome cannot hide a per-account discrepancy.

The Playground now demonstrates a two-account transfer in which one TRANSFER record debits the source and credits the destination, then compares both gross balances. A negative sample omits the source account; the ledger projection rejects the event before destination credit, and the account-set result remains unresolved even though the separate synthetic aggregate balance is satisfied.

RES19-20 remains BOUNDED with both ledger and account-set tests. RES19-21 is now BOUNDED for the canonical single-record TRANSFER model: the source-less event is rejected before destination credit. This does not introduce a separate debit/credit event model. The wrapper is not a cross-account conservation invariant, does not authenticate measurements or event-batch completeness, and does not complete the full RESOURCE-RECONCILED stage. The canonical v1.9 source and its 60 expected fixture outcomes are unchanged.

### 2026-11-19 — exact v1.9 contract-version identity boundary

Resource preflight now requires and returns an opaque contract-version reference. Time-scoped reconciliation requires the caller to carry that exact reference into the reconciliation contract, and requires the report batch and every report event to use the same identity. Missing or mismatched identities remain unresolved; no semantic-version ordering, cross-version compatibility, migration or evidence authentication is inferred. Event idempotency fingerprints also retain the report version, and the Playground includes a deterministic mismatch sample.

RES19-54 is now PARTIAL, not BOUNDED: exact identity mismatch detection is implemented and tested, but compatibility between different contract versions remains undefined. The locked v1.9 canonical document and its 60 normative expected outcomes are unchanged.


### 2026-11-21 — direct timestamp parser regression coverage

Added a focused test suite for the shared v1.9 temporal primitive. The tests exercise Gregorian leap-year and impossible-date validation, clock-field and explicit-offset syntax, the existing one-to-nine fractional-digit limit, and exact offset-equivalent ordering across UTC date/year rollovers. These tests lock the current bounded implementation profile only; they do not define universal endpoint semantics, timestamp provenance, clock accuracy or a new canonical timestamp format. The v1.9 source and its 60 normative fixture outcomes remain unchanged.


### 2026-11-22 — prototype-safe account identifiers

The append-only ledger projection now stores dynamic account identifiers as own enumerable data properties before applying arithmetic. This prevents JavaScript's inherited `__proto__` setter from swallowing an account balance write or making a debit appear applied without changing the projected value. Stable regression `RES19-LEDGER-025` transfers from an account named `__proto__` and checks the resulting gross, reserved and available balances. This is implementation hardening for the identifier representation, not a new v1.9 account-naming restriction. The locked canonical source and its 60 normative expected outcomes remain unchanged.


### 2026-11-25 — structured malformed v1.9 ledger inputs

The public ledger projection now validates its top-level account/event collections, rejects null or non-record entries, and checks required and optional field types before using string operations or serialising idempotency content. Invalid entries are not applied and receive explicit malformed diagnostics; valid entries in the same supplied batch may still be projected, but the overall result remains `LEDGER-MALFORMED`. This does not silently coerce values or change the canonical event model.

Stable regression `RES19-LEDGER-026` covers non-array collections, null account/event entries, a non-string account identity and a non-string optional source reference. The canonical v1.9 source and all 60 normative expected fixture outcomes remain unchanged. This is an implementation input-validation boundary, not evidence authentication or a new resource rule.


### 2026-11-26 — bounded RESOURCE-RECONCILED stage composition

Added a pure stage coordinator that composes the existing resource preflight, caller-supplied attempt and report evidence, scalar conservation evaluation, and account-set gross-balance reconciliation. The coordinator requires RESOURCE-READY, passing attempt/report assertions, exact opaque contract-version identity across preflight and report inputs, and the same observation instant for the conservation contract and complete event batch. Every account must still have exactly one accepted measured observation against the same ordered ledger projection.

The result is RESOURCE-RECONCILED only when all required stage assertions, the scalar-additive conservation contract and every account comparison pass. A fully evidenced conservation mismatch or account discrepancy returns RESOURCE-RECONCILIATION-FAILED; incomplete or contradictory evidence remains RESOURCE-OUTCOME-UNKNOWN; malformed contracts/account sets remain invalid. The result is explicitly limited to one resource kind, one exact unit contract, the supported scalar-additive invariant and the supplied account set. It does not infer a cross-account invariant, authenticate evidence, implement transformations or conversions, run an executor, or verify a target postcondition.

Stable tests RES19-STAGE-001–007 cover success, mismatch, unresolved stage evidence, exact version identity, observation-time alignment, malformed account sets and deterministic read-only behaviour. Playground tests RES19-PREVIEW-012–013 expose the bounded result and preserve mismatch/unknown distinctions. The canonical v1.9 document and its 60 normative expected outcomes remain unchanged; RES19-40 stays PARTIAL for the wider contract.

### 2026-11-26 — missing account-set batch-evidence guard

The account-set wrapper now validates that its required event-batch evidence record is present and non-array object-shaped before composing per-account results. Previously, each nested account comparison could report a missing record as invalid, but the wrapper then dereferenced the absent record while constructing its aggregate result, allowing malformed input to throw instead of returning a structured outcome. The stage coordinator now preserves the same explicit `INVALID-RECONCILIATION` result for missing, null or array-shaped batch evidence.

Stable regressions `RES19-RECON-028` and `RES19-STAGE-008` cover absent, null and array-shaped evidence at the account-set and stage boundaries. The locked v1.9 source and its 60 normative fixture outcomes remain unchanged; this is implementation input-validation hardening only.
