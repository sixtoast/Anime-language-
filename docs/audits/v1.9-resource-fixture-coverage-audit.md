# Arcane Incantations v1.9 — fixture-to-implementation coverage audit

**Status:** Engineering audit; not canonical specification.  
**Audited source:** `docs/canon/arcane-incantations-v1.9-resource-accounting-and-conservation-contracts.md`  
**Source fixtures:** 60 normative expected outcomes.  
**Implementation branch baseline:** `bbcced72fab93ce86905a96a3b80b1c96abad5ce` (v1.9 development branch).

## Purpose and interpretation

This audit connects each of the 60 canonical v1.9 design fixtures to the current resource preflight, ledger projection, conservation evaluator, account reconciler and separate gate tests.

It does **not** execute the 60 specification fixtures. It does not change their expected outcomes, promote implementation behaviour to canon, or claim that a bounded evaluator implements the entire normative contract.

- **BOUNDED:** the linked tests cover the stated bounded behaviour under the implementation's explicit assumptions. This is not a claim that every part of the normative case is complete.
- **PARTIAL:** some relevant behaviour is enforced, but one or more important parts of the fixture remain unimplemented or caller-supplied.
- **SEPARATE-GATE:** the fixture concerns an independent authority/policy gate; it is intentionally not decided by resource accounting.
- **SPECIFICATION-ONLY:** no executable implementation is claimed for the fixture.

A linked test ID identifies implementation regression evidence in the workbench registry. It is not a proof of external evidence authenticity, physical validity or execution.

The automated audit test also verifies that every distinct linked ID resolves to exactly one registry entry, its declared source path remains inside the repository, and its marker appears exactly once in that source test file. This protects traceability metadata; it does not prove that a test has run. Execution evidence still comes from the exact-commit CI workflow.

## Current implementation modules

- `resourcePreflight.ts`: bounded scalar availability; caller-supplied source availability windows and provenance references are checked against an explicit evaluation time, with stale values rejected and ambiguous endpoints left unresolved; source/budget evidence states, held-reservation arithmetic and conservative budget upper bounds.
- `resourceLedger.ts`: deterministic integer-tick projection for supported source-entry, transfer, reservation, consumption, measured-return and loss events; generic transformations, corrections, external exchanges and reconciliation events are not applied.
- `reservationExpiry.ts`: pure temporal assessment using explicit Unix-millisecond timestamps; it requires caller-supplied observed-expiry or contractual-guarantee evidence after the expiry time, leaves the exact boundary unresolved, and never mutates ledger availability.
- `resourceConservation.ts`: one-resource, one-unit-contract scalar-additive balance evaluation and single-account gross-balance comparison.
- `resourceConservationPreview.ts`: synthetic, deterministic Playground samples only.
- `authorityDecision` and `policyProfileComposition` modules: separate gate concerns; their results are not resource evidence or execution.

## Explicit gaps retained

The current implementation does not supply dimension-vector conservation, source-contract authentication, probabilistic uncertainty models, expiry-driven ledger state transitions or release-policy integration, reservation identity/state resolution, authenticated expiry evidence, concurrent/distributed reservation guarantees, availability-window endpoint policy, valid transformation contracts, complete boundary discovery, executor transaction semantics, partial execution, interruption/recovery, compensation, refund semantics, distributed-ledger consistency, contract-version reconciliation, whole-resource reconciliation, versioned audit-record construction or target postcondition verification.

No generic mana-to-energy conversion, unit conversion, resource equivalence, new tolerance, physical law or spoken form is introduced by this audit.

## Next step

The temporal expiry assessment is deliberately separate from ledger projection. Integrate an expiry-driven ledger transition only after the applicable release-policy effect and endpoint semantics are defined; do not free availability merely because the timestamp has passed. Continue to select gaps only where the canonical domain contract, evidence requirements and negative fixtures are sufficiently defined.
